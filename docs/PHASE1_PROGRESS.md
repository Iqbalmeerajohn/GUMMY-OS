# GUMMY OS — Phase 1 Progress

> Engineering progress report for **Phase 1: The Memory Engine** — the persistent,
> consent-based long-term memory that every future agent in GUMMY OS depends on.
> Organized by completed engineering milestone, not by calendar.

**Status:** Phase 1 core complete and verified. **Backend:** FastAPI · PostgreSQL
(Supabase) · pgvector · SQLAlchemy 2.x · Alembic · Hugging Face embeddings ·
Anthropic Claude. **Quality gate (all green):** Ruff · Black · mypy · pytest.

---

## Overview

Phase 1 builds the **Memory Engine** — the foundation that lets GUMMY OS deliver a
genuinely *personalized* AI experience rather than a stateless chatbot. The thesis
of the product is that **memory is the moat**: an assistant is only as useful as
what it durably remembers about you, how well it recalls the *right* thing at the
*right* moment, and how transparently you can inspect and control that memory.

This phase delivers the full vertical slice of that engine: storing distilled
memories, embedding them for semantic search, ranking them with a hybrid relevance
model, reinforcing the ones that prove useful, and assembling them into grounded
context for a memory-aware chat — end to end, behind a clean, tested, production-
minded API.

## Completed Milestones

### Task 1: Backend Foundation

A production-grade FastAPI service skeleton with the engineering discipline to
scale to a team.

- **FastAPI scaffold** — app factory (`create_app`) + lifespan management; the
  ASGI app served by `uvicorn app.main:app`.
- **Layered project structure** — strict inward dependency rule
  (`api → services → repositories → database`) so business logic never leaks into
  HTTP handlers or SQL.
- **Configuration system** — typed `pydantic-settings`, loaded from environment /
  `.env`, with safe defaults so the app boots before every integration is wired.
- **Health endpoints** — `/health` (liveness) and `/health/ready` (readiness with a
  dependency check), returning `503` only when a *configured* dependency is down.
- **Testing setup** — `pytest` + `pytest-asyncio` with an ASGI test client; smoke
  tests that run with zero external services.
- **CI readiness** — structured JSON logging, a consistent error envelope, Docker
  packaging, and tooling (Ruff/Black/mypy/pytest) wired so CI is green from day one.

**Outcome:** A trustworthy, observable, deployable service shell — every later
feature plugs into a clean seam instead of a pile of glue code.

---

### Task 2: Database Foundation

A multi-tenant, migration-driven relational core, designed for SaaS from the first
table.

- **PostgreSQL integration (Supabase)** — async engine with connection pooling;
  pooled vs. direct (non-pooled) URLs separated for runtime vs. migrations.
- **SQLAlchemy 2.x** — typed declarative models with a deterministic constraint/
  index naming convention (so autogenerated migrations stay clean).
- **Alembic migrations** — async, settings-driven; the schema is reproducible and
  version-controlled, never hand-applied.
- **`User` model** — the tenancy root; every record is `user_id`-scoped.
- **`Memory` model** — the semantic long-term store: category, content,
  importance/confidence scores, lifecycle status, soft-delete, recall tracking.
- **`MemoryVersion` model** — an append-only history snapshot of every memory
  change, with a versioned audit trail.

**Outcome:** A durable, multi-tenant, evolvable data model — the system of record
the entire Memory Engine is built on, safe to migrate and scale.

---

### Task 3: Memory Lifecycle System

Full CRUD with auditable lifecycle semantics — memories are first-class, versioned,
recoverable artifacts.

- **Create memory** — with default scoring and an initial version snapshot.
- **Update memory** — partial updates that append a new version **only when content
  changes** (no audit noise for score-only edits).
- **Archive memory** — reversible status change that preserves history (and records
  an `archived` version event); idempotent.
- **Soft delete** — recoverable deletion (`deleted_at`), excluded from default
  reads while history survives.
- **Version tracking** — every content change, edit, and lifecycle transition is
  captured as an immutable `MemoryVersion`.
- **CRUD APIs** — `POST/GET/PATCH/DELETE /api/v1/memories`, plus `…/archive`, all
  tenant-scoped with a clean error envelope.

**Outcome:** Users (and future agents) can manage memory with full transparency and
no data loss — the backend embodiment of *"you own your memory."*

---

### Task 4: Semantic Memory Layer

Memories become *searchable by meaning*, not just by exact match.

- **pgvector** — the `vector` extension enabled via migration; an HNSW cosine index
  for fast approximate-nearest-neighbour search.
- **Memory embeddings** — a dedicated `memory_embeddings` table (decoupled from the
  hot memory row) supporting re-embedding and multiple/upgraded models.
- **Hugging Face embeddings** — `all-MiniLM-L6-v2` (384-dim) behind a provider
  interface: lightweight, CPU-friendly, **zero per-call cost**; lazy-loaded and
  optional, with a deterministic fake provider for tests.
- **Semantic search** — tenant-scoped, live-only cosine ranking computed in the
  database (`<=>`), not in Python.
- **Similarity ranking** — content-hash dedupe avoids redundant work; results are
  returned nearest-first with a similarity score.

**Outcome:** Recall by *meaning* — "companies I applied to" finds the relevant
memories even when the words don't match. This is the retrieval substrate agents
will stand on.

---

### Task 5: Hybrid Retrieval Engine

Semantic similarity alone isn't enough; this milestone decides *what actually
matters right now*.

- **Importance scoring** — how much a memory matters (identity/goals high, trivia
  low), with time decay.
- **Confidence scoring** — how sure the system is a memory is true.
- **Recency scoring** — exponential decay with a 30-day half-life, favoring fresh /
  recently-used memories.
- **Reinforcement** — retrieved memories get "stickier": recall is counted and
  scores bump with **diminishing returns, a hard cap, and a cooldown** so bursts
  can't inflate them.
- **Retrieval ranking** — a weighted hybrid (semantic + importance + confidence +
  recency, weights summing to 1.0) that over-fetches candidates and re-ranks,
  defeating both "forgot the obvious" and "drowned in trivia."
- **Background embedding sync** — a lightweight in-process async worker (with
  retries + failure handling) keeps embeddings fresh automatically on memory
  create/update — no manual step.

**Outcome:** The system surfaces the *right* memories, learns which ones earn their
keep, and stays current on its own — the intelligence layer of recall.

---

### Task 6: Memory-Aware Chat Foundation

The engine becomes conversational: retrieved memory is turned into a grounded
answer.

- **Context assembly** — dedupe → rank → **token-budgeted** selection into a
  provider-agnostic context package.
- **Prompt builder** — composes a system persona + grounding instruction + the
  `<memory>` block + the user query into a clean prompt payload.
- **Claude gateway** — the Anthropic async SDK behind a provider interface:
  configurable model (default `claude-opus-4-8`), client-level timeout + automatic
  retries, and provider errors normalized to typed app errors (never a raw 500).
- **Memory-aware chat API** — `POST /api/v1/chat`: retrieval → assembly → prompt →
  model → reply, with usage metadata.
- **Provider abstraction** — a one-method `LLMProvider` Protocol; adding OpenAI or
  Gemini later is a new class + a factory branch, with the chat service unchanged.

**Outcome:** GUMMY can answer questions *grounded in what it remembers about you* —
the first tangible, personalized AI experience the whole engine was built to enable.

## Key Architecture Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| **Layering** | `api → services → repositories → database` | Business logic and SQL never leak into HTTP handlers; each layer is independently testable. |
| **Multi-tenancy** | `user_id` on every row from day one | SaaS-ready isolation without a later rewrite (RLS is a hardening pass on top). |
| **Schema evolution** | Alembic migrations only (no `create_all` in prod) | Reproducible, reviewable, reversible schema; deterministic constraint/index naming for clean diffs. |
| **Vectors** | Dedicated `memory_embeddings` table (not an inline column) | Re-embedding and multiple/upgraded models without bloating the hot memory row. |
| **Vector search** | pgvector cosine + HNSW, ranked **in the database** | ANN performance and a single source of truth; no Python-side scan. |
| **Embedding provider** | Provider interface; HF `all-MiniLM-L6-v2` (384-d), lazy + optional | Zero per-call cost, CPU-friendly; a deterministic fake keeps tests fast/offline; swappable for an API later. |
| **Relevance** | Hybrid weighted score (semantic + importance + confidence + recency, Σ=1) | Beats pure similarity; defeats "forgot the obvious" and "drowned in trivia." |
| **Reinforcement** | Diminishing step + hard cap + cooldown | Useful memories get stickier without burst-gaming the scores. |
| **Embedding sync** | In-process `asyncio` worker with retries | Fresh embeddings off the request path; swappable for Redis/Celery at scale. |
| **LLM access** | Provider-abstracted Claude gateway (async SDK) | Configurable model, timeout + auto-retry, errors normalized to typed `AppError`; OpenAI/Gemini drop in later. |
| **Versioning** | Append-only `memory_versions` | Full, auditable history; supersession over silent overwrite. |
| **Soft delete** | `deleted_at` + recoverable reads | "Right to be forgotten" with a recovery window; history survives. |

## Current Capabilities

GUMMY OS can, today:

- **Store** distilled memories across categories with importance/confidence scores,
  lifecycle status, soft-delete, and recall tracking — all tenant-scoped.
- **Version** every memory change as an immutable, auditable history.
- **Manage** memories over a full REST API (create, read, list/filter, update,
  archive, soft-delete).
- **Embed** memory content into 384-dim vectors automatically on create/update via a
  background worker (with retries), deduping unchanged content.
- **Search semantically** over a user's memories using pgvector cosine similarity.
- **Retrieve** the most relevant memories with a **hybrid** score (semantic +
  importance + confidence + recency) and **reinforce** the ones it surfaces.
- **Assemble** retrieved memories into a token-budgeted context package and build a
  grounded prompt.
- **Chat** — answer a user's question grounded in their remembered context via the
  Claude gateway, returning the reply plus usage metadata.
- **Operate cleanly** — structured logging, a consistent error envelope, health
  probes, reproducible migrations, and a green Ruff/Black/mypy/pytest gate.

## Known Limitations

Intentionally **not** implemented in Phase 1 (deferred by design):

- **No authentication / authorization** — the tenant is passed explicitly as a
  `user_id` parameter behind a single dependency seam (the placeholder that auth
  replaces).
- **No Row-Level Security (RLS)** — tenant isolation is enforced in the application
  layer; database-level RLS is a hardening pass.
- **No streaming responses** — chat returns a complete reply (non-streaming).
- **No conversation/session persistence** — chat is single-turn; messages and
  rolling summaries are not yet stored.
- **No agents / orchestration** — no multi-agent system, tool use, LangGraph, RAG
  framework, browser automation, voice, or vision.
- **Live-path validation pending** — pgvector ranking and real Claude calls are
  proven via compiled SQL and fakes; an end-to-end run against live Supabase +
  Anthropic has not yet been executed.

## Resume Value

Phase 1 demonstrates the end-to-end AI-engineering skill set behind a modern,
memory-centric LLM product:

- **Retrieval-augmented memory systems** — a custom memory layer with embeddings,
  vector search, and a **hybrid relevance model** (semantic + importance +
  confidence + recency), including reinforcement with anti-gaming safeguards.
- **Vector search with pgvector** — schema design, HNSW indexing, and tenant-scoped
  cosine ranking computed in PostgreSQL.
- **Embedding engineering** — provider-abstracted Hugging Face (`all-MiniLM-L6-v2`)
  embeddings, content-hash dedupe, and a background (re)embedding worker with
  retries and failure handling.
- **LLM application architecture** — a provider-abstracted Claude gateway (Anthropic
  async SDK) with timeout/retry handling and normalized errors, token-budgeted
  context assembly, and a grounded prompt-building pipeline.
- **Production backend engineering** — FastAPI with clean layering, async
  SQLAlchemy 2.x, Alembic migrations, multi-tenant data modeling, structured
  logging, and Docker.
- **Software quality discipline** — 87 automated tests across unit/DB/API layers, a
  fast offline test strategy (fakes + compiled-SQL verification), and an enforced
  Ruff/Black/mypy/pytest quality gate.
- **System design judgment** — swappable seams (embeddings, LLM, storage), explicit
  scope boundaries, and migration-driven, no-rewrite evolution toward multi-tenant
  SaaS.
